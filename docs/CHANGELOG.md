#### Фикс — создание заказа после включения RLS на Production (2026-08-30)

##### 🗄️ [DATABASE] + 🍳 [KITCHEN/CRM]
* **Заказ с витрины не долетал до менеджера после включения RLS**. Причина: `createOrderInSupabase` делал `INSERT ... RETURNING` (`.select()` в supabase-js), а у анонимного ключа после `00013` нет (и не должно быть) права SELECT на `orders` — PostgREST не мог вернуть строку и **откатывал всю вставку**. Заказ оседал только в `localStorage` устройства с фиктивным `id` (`order-<timestamp>`), из-за чего потом и чат заказа падал с `400` (нельзя привести `order-...` к `uuid`).
* **Решение**: новая функция [`supabase/migrations/00014_create_client_order_rpc.sql`](../supabase/migrations/00014_create_client_order_rpc.sql) — RPC `public.create_client_order(...)` (`SECURITY DEFINER`, обходит RLS), возвращает настоящий UUID заказа. Витрина ([`lib/orders/orders.ts`](../lib/orders/orders.ts)) создаёт заказ только через эту RPC; прямая анонимная вставка убрана, политика `orders_anon_insert` удалена. Требует ручного применения на Production Supabase (после `00013`). Синхронизировано в [`supabase/full_schema.sql`](../supabase/full_schema.sql).
* **Новый заказ не всплывал у менеджера в реальном времени** (только после F5), хотя сообщения чата доходили мгновенно. Причина: Supabase Realtime подчиняется RLS — по таблице `order_chat_messages` (SELECT открыт всем) события шли, а по `orders` (SELECT только `MANAGER`/`ADMIN`) сокет должен быть авторизован токеном вошедшего, а подписка стартовала раньше, чем токен доезжал до сокета. В [`lib/orders/orders.ts`](../lib/orders/orders.ts) `subscribeToOrdersRealtime` теперь перед подпиской берёт `access_token` текущей сессии и передаёт его в `supabase.realtime.setAuth(...)`. Код-только, без миграций.

##### 🛡️ [SECURITY] — настройка Supabase (без кода)
* **Сессия менеджера отваливалась досрочно** (401 на чтение заказов, «заказы перестали доходить», лечилось только ручным перезаходом). Причина: в Supabase был включён «Detect and revoke potentially compromised refresh tokens» с окном повторного использования `10` секунд, а токен продлевали одновременно и middleware, и браузерный клиент — вторая попытка вне окна считалась взломом и отзывала всю сессию. Решение: **«Refresh token reuse interval» поднят до `300` секунд** (максимум) в Authentication → Sessions. Проверено: 2+ часа активной работы менеджера без перезахода.

  * Глобальное правило «поля ввода ≥16px на телефоне» ([`app/globals.css`](../app/globals.css)) не действовало, потому что компоненты задавали `fontSize` инлайн (`0.9–0.95rem`), а инлайн-стиль перебивает таблицу стилей. Инлайн-размеры сняты с полей формы доставки ([`components/CartDrawer.tsx`](../components/CartDrawer.tsx)) и панели «Мои заказы» ([`components/MyOrdersPanel.tsx`](../components/MyOrdersPanel.tsx)); базовый размер `0.95rem` для десктопа перенесён в CSS, медиазапрос `≤768px → 16px` теперь реально применяется.
  * Прокрутка страницы под открытой панелью не блокировалась — фон скроллился «сквозь» фиксированный оверлей (iOS scroll-chaining) и панель уезжала. Добавлен хук [`hooks/useBodyScrollLock.ts`](../hooks/useBodyScrollLock.ts) (`overflow: hidden` на `body` + компенсация полосы прокрутки), подключён в `CartDrawer`, `MyOrdersPanel`, `OtpVerificationModal`, `ClientOrderChatModal`.
  * Высота выезжающих панелей переведена с `100%` на `100dvh`, добавлен `overscroll-behavior: contain`; оверлей модалки OTP получил `overflow-y: auto` на случай, когда клавиатура делает окно выше экрана.
  * **Обрезанное окно чата с менеджером** ([`components/ClientOrderChatModal.tsx`](../components/ClientOrderChatModal.tsx)): у модалки была жёсткая высота `520px` при вертикальном центрировании — на невысоком экране и при открытой клавиатуре шапка и поле ввода уходили за край. Высота переведена на `min(520px, calc(100dvh - 32px))`, оверлею добавлен `overflow-y: auto`, с поля ввода снят инлайн `fontSize` (теперь 16px на телефоне — без зума).
  * **Окно «Подробнее» о блюде открывалось не по центру экрана** ([`app/page.tsx`](../app/page.tsx)): на корне страницы висит `.animate-fade-in` с постоянным `transform` (`animation-fill-mode: forwards`), а `transform` у любого предка превращает `position: fixed` в позиционирование относительно этого предка — окно «уезжало» в середину списка блюд, тем сильнее, чем ниже была прокрутка. Модалка блюда теперь рендерится React-порталом в `<body>`, вне трансформированного контейнера; добавлены блокировка прокрутки фона и `max-height: calc(100dvh - 40px)`.

### 📌 Версия v1.0.2 — Подключение боевой БД после деплоя (28.08.2026)
* **Источник**: заказчик сообщил, что заказы, сообщения и новые блюда видны только на его ноутбуке, а с других устройств (второй ноутбук, телефон) не доходят.

#### 🗄️ [DATABASE] & 🍳 [KITCHEN/CRM]
* **Найдена и устранена причина «работает только на моём устройстве»**: на боевом Supabase у таблиц `dishes`, `orders` и `order_chat_messages` был включён Row Level Security **без единой политики** (Supabase включает RLS автоматически при создании таблицы через Table Editor). Из-за этого анонимный ключ витрины не мог ни писать, ни читать, а весь код данных ([`lib/menu/dishes.ts`](file:///C:/Users/Bergmann/Desktop/angular/%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%8B/kan-ban_cafee_bestellungen_trello/lib/menu/dishes.ts), [`lib/orders/orders.ts`](file:///C:/Users/Bergmann/Desktop/angular/%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%8B/kan-ban_cafee_bestellungen_trello/lib/orders/orders.ts), [`lib/orders/chat.ts`](file:///C:/Users/Bergmann/Desktop/angular/%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%8B/kan-ban_cafee_bestellungen_trello/lib/orders/chat.ts)) молча уходил в localStorage-подстраховку — данные жили только в одном браузере. Переменные окружения на Vercel (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) были корректны, повторный деплой не потребовался. RLS отключён на трёх таблицах (Database → Policies → Disable RLS) — заказы, сообщения и публикация блюд теперь синхронизируются между всеми устройствами и в обе стороны. Состояние зафиксировано комментарием в [`supabase/full_schema.sql`](file:///C:/Users/Bergmann/Desktop/angular/%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%8B/kan-ban_cafee_bestellungen_trello/supabase/full_schema.sql).
* **Колонка `image_url` в таблице `dishes`**: форма публикации блюда сохраняет фото (сжатый Canvas-JPEG в виде data URL), но колонки под него в боевой БД не было — INSERT блюда с фотографией отклонялся целиком, и блюдо оседало только в localStorage. Колонка добавлена вручную на Production и зафиксирована в [`supabase/full_schema.sql`](file:///C:/Users/Bergmann/Desktop/angular/%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%8B/kan-ban_cafee_bestellungen_trello/supabase/full_schema.sql) + миграции [`supabase/migrations/00009_dishes_image_url.sql`](file:///C:/Users/Bergmann/Desktop/angular/%D0%BF%D1%80%D0%BE%D0%B5%D0%BA%D1%82%D1%8B/kan-ban_cafee_bestellungen_trello/supabase/migrations/00009_dishes_image_url.sql). Проверено в браузере: блюдо с фото, опубликованное на компьютере, появляется на телефоне с правильной картинкой.
