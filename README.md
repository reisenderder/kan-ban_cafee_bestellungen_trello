# kan-ban_cafee_bestellungen_trello

## Универсальные правила проекта

Эти правила действуют для всего проекта и проверяются перед каждым следующим шагом.

1. Документация, спецификации, планы и пользовательские тексты пишутся на русском языке.
2. Проект ведется по алгоритму: `Spec -> Plan -> Code`.
3. Нельзя реализовывать функцию, если она не описана в утвержденной спецификации.
4. Если новая идея противоречит Global Spec, работа останавливается до уточнения.
5. Корневые правила важнее правил папок; правила папок уточняют порядок работы внутри своего раздела.
6. Клиентские данные должны раскрываться только по роли, задаче и текущему контексту.
7. Любое новое правило добавляется только если оно предотвращает ошибку, экономит время или делает процесс стабильнее.
8. После сообщения `pull request смержен` работа синхронизируется с актуальной веткой `main`; каждая новая задача начинается в новой ветке от `main`.
9. Если один Work Plan разделен на несколько групп, одновременно выполняется только одна группа: для нее создается отдельная ветка от актуального `main`, а следующая группа начинается после merge и синхронизации `main`.

## Структура

* `.agents/` - правила и материалы для AI-агентов.
* `specs/` - спецификации, функциональные карты и продуктовая документация.
* `work_plans/` - планы разработки и история их выполнения.
* `work_plans/active/` - активные планы, работа по которым еще не завершена или еще не подтверждена пользовательским тестированием.
* `work_plans/completed/` - завершенные планы, сохраненные как история выполненных работ.
* `roadmap/` - хронологическая история фактически завершенных работ по областям проекта.

## Жизненный цикл планов разработки

1. Новый план разработки создается в `work_plans/active/`.
2. План остается в `active/`, пока не завершены все его группы и задачи, даже если отдельная группа уже реализована, проверена или смержена.
3. Для промежуточных этапов активного плана разрешены `git add`, commit, push, pull request и merge после явного запроса пользователя на соответствующее Git-действие. Эти действия не означают завершение всего плана.
4. План считается завершенным только после того, как:
   * выполнены все группы и критерии готовности плана;
   * пользователь вручную проверил итоговый результат;
   * пользователь явно подтвердил завершение всего плана и попросил подготовить его финальную публикацию.
5. После этого подтверждения и до финального push, который делает изменения готовыми к merge, файл плана перемещается из `active/` в `completed/`.
6. В той же финальной группе изменений обновляются статус плана, индекс `work_plans/README.md` и все ссылки на файл.
7. Одновременно в соответствующие журналы `roadmap/` добавляются хронологические записи о фактически выполненных работах:
   * данные;
   * backend и инфраструктура;
   * frontend и дизайн;
   * искусственный интеллект и AI-анализ.
8. Если план затрагивает несколько областей, запись добавляется в каждый соответствующий журнал.
9. Перенос плана и обновление roadmap включаются в финальный completion commit до публикации, после которой pull request готов к merge.
10. Завершенный план и записи roadmap не удаляются: они сохраняют историю разработки.

AI-агент не переносит план в `completed/` только на основании завершения отдельной группы, кода, автоматических тестов или промежуточного pull request. Для переноса требуется явное подтверждение пользователя после ручной проверки всего плана.

Обновление roadmap является обязательной частью финального завершения плана. В roadmap записываются только выполненные и проверенные результаты всего плана, а не промежуточные намерения.
