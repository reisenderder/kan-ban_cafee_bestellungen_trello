## 1. Назначение

План проводит сплошную ревизию проекта DAYMOHKCOFEE по двадцати двум зонам аудита и фиксирует каждое расхождение как проверяемую находку с доказательством.

План отвечает на три вопроса:

1. Соответствует ли реализация утверждённым требованиям — по каждому критерию приёмки, а не в целом.
2. Есть ли в реализации поведение, не имеющее основания в требованиях.
3. Где в проекте накоплен технический, документационный и эксплуатационный долг, и какова его цена.

Результат плана — не исправленный проект, а **достоверная карта его состояния**, пригодная для того, чтобы на её основе составить план исправлений.

## 2. Границы плана

### 2.1. Что план делает

* Читает код, документацию, миграции, конфигурацию и историю репозитория.
* Выполняет проверки только для чтения: `npm run typecheck`, `npm run lint`, `npm run build`, статический анализ, поиск по файлам.
* Записывает наблюдения в отчёты `../../docs/audit/`.
* Формирует единый реестр находок и приоритизацию.

### 2.2. Что план не делает

* Не изменяет ни одной строки кода.
* Не изменяет ни одной спецификации в `../../specs/`.
* Не изменяет схему базы данных и не выполняет запросов, изменяющих данные.
* Не создаёт новых требований. Наблюдение аудитора не становится требованием — оно становится входом для отдельного плана исправлений.
* Не выполняет исправлений даже очевидных: опечатка в коде, неиспользуемый импорт, отсутствующий тип фиксируются как находки, но не правятся.

Обоснование запрета на исправления: смешивание ревизии и правки делает реестр находок недостоверным — невозможно отличить «этого не было» от «это исправили по ходу», а база аудита перестаёт быть неподвижной.

## 3. Методология

Шесть правил. Они обязательны для каждого эпика и не подлежат смягчению по ходу работы.

### 3.1. Правило первое: иерархия источников истины

При любом расхождении приоритет определяется правилом 10 документа `../../specs/RULES.md`:

```
Global Spec → Functional Map → Feature Specs → Technical Specs → User Stories → Work Plans → CHANGELOG → код
```

Код — нижний уровень. Находка всегда формулируется относительно вышестоящего документа: не «спецификация не соответствует коду», а «код не соответствует спецификации». Обратная формулировка допустима только тогда, когда расхождение обнаружено между двумя документами, и тогда указывается, какой из них выше.

### 3.2. Правило второе: доказательность

Находка без доказательства в реестр не попадает. Доказательством считается одно из трёх:

1. **Ссылка на строки**: `путь/файл.tsx:127-134`. Указываются конкретные строки, а не файл целиком.
2. **Дословная цитата из документа** с указанием файла и параграфа.
3. **Воспроизводимая команда и её фактический вывод**, приведённый в отчёте без пересказа.

В отчётах запрещены формулировки «кажется», «вероятно», «скорее всего», «по-видимому». Если проверить утверждение не удалось — оно получает статус `NOT-VERIFIED` с указанием причины и того, что требуется для проверки. Непроверенное утверждение не становится находкой.

### 3.3. Правило третье: аудит ничего не чинит

См. пункт 2.2. Любое желание поправить фиксируется как находка с полем «Решение», которое является предложением, а не выполненным действием.

### 3.4. Правило четвёртое: неподвижная база

В эпике 0 фиксируется SHA коммита ветки `main`. Весь аудит проводится против этого состояния. Любая ссылка вида `файл:строки` означает «эти строки в зафиксированном коммите».

Если за время работы `main` уходит вперёд, база не переносится. Расхождение фиксируется явно в эпике 23: базовый SHA, конечный SHA, перечень коммитов между ними и оценка того, затрагивают ли они находки.

### 3.5. Правило пятое: двусторонняя проверка

Каждая зона проверяется в обе стороны:

* **Прямая**: требование → есть ли реализация.
* **Обратная**: реализация → есть ли требование.

Односторонняя проверка систематически пропускает недокументированное поведение, поэтому обратное направление вынесено в отдельный эпик 1.4 и обязательно к выполнению.

### 3.6. Правило шестое: работа с непроверяемым

Пять зон (14, 15, 19, 20, 22) невозможно проверить по содержимому репозитория. Для них аудит выдаёт:

1. то, что всё же проверяемо из кода и документов, — как обычные находки с доказательством;
2. структурированный опросник с точными вопросами;
3. явный перечень `NOT-VERIFIED` с указанием, что именно требуется для проверки и от кого.

Домысливание ответов вместо опросника запрещено.

## 4. Классификатор находок

### 4.1. Идентификатор

Формат: `AUD-<эпик>-<NNN>`, где `<эпик>` — номер эпика по разделу 7, `<NNN>` — сквозной трёхзначный номер внутри эпика.

Примеры: `AUD-1.1-014`, `AUD-5-003`, `AUD-16-002`.

Идентификатор присваивается один раз и не меняется. Отклонённая находка сохраняет свой номер со статусом `REJECTED` — номера не переиспользуются.

### 4.2. Критичность

| Код | Название | Определение |
| --- | --- | --- |
| `S0` | Блокер | Делает функцию непригодной к использованию или ведёт к потере данных. Требует немедленного решения. |
| `S1` | Критично | Нарушает утверждённое требование в основном пути; заметно пользователю или персоналу. |
| `S2` | Существенно | Нарушает требование в отклонении или граничном случае; создаёт заметный долг. |
| `S3` | Незначительно | Отклонение без прямого влияния на поведение: качество кода, полнота документации. |
| `S4` | Косметика | Опечатки, форматирование, единообразие формулировок. |

**Критичность зависит от стадии проекта.** Одно и то же наблюдение имеет разную цену на разных стадиях, поэтому критичность присваивается относительно стадии, объявленной в эпике 0, и рядом с кодом указывается эта стадия.

Примеры стадийного сдвига:

| Наблюдение | Прототип | MVP | Предрелиз | Эксплуатация |
| --- | --- | --- | --- | --- |
| Отсутствует резервное копирование | `S3` | `S2` | `S1` | `S0` |
| Политики доступа на уровне строк отключены | `S3` | `S2` | `S0` | `S0` |
| Нет политики конфиденциальности | `N/A` | `S3` | `S0` | `S0` |
| Контур реализован заглушкой | `N/A` | `S2` | `S1` | `S0` |
| Автоматические тесты отсутствуют | `S4` | `S3` | `S2` | `S2` |
| Нет метаданных для поисковых систем | `N/A` | `S4` | `S2` | `S2` |

Правило применения: если находка сохранится к следующей стадии, в поле «Влияние» указывается её будущая критичность. Это не позволяет отложенной находке потеряться при переходе проекта на следующую стадию.

### 4.3. Статус

| Код | Значение |
| --- | --- |
| `OPEN` | Зафиксирована, доказательство приведено, не рассмотрена пользователем. |
| `CONFIRMED` | Подтверждена пользователем как подлежащая исправлению. |
| `REJECTED` | Отклонена: поведение признано намеренным. Причина записывается. |
| `DEFERRED` | Признана верной, но отложена. Причина и условие возврата записываются. |
| `NOT-VERIFIED` | Проверить не удалось. Причина и требуемое для проверки записываются. |
| `N/A` | Неприменимо на объявленной стадии проекта: проверять нечего, потому что проверяемого ещё не должно существовать. Записывается стадия, начиная с которой зона становится применимой. |

### 4.4. Тип

`Расхождение со спецификацией` · `Дефект` · `Пробел в документации` · `Недокументированное поведение` · `Технический долг` · `Улучшение` · `Вопрос к пользователю`

**Различие `NOT-VERIFIED` и `N/A`.** Эти статусы смешивать нельзя. `NOT-VERIFIED` означает «проверка возможна, но не выполнена — не хватает доступа, данных или ответа пользователя». `N/A` означает «проверять нечего: на этой стадии проекта отсутствие проверяемого является нормой, а не дефектом». Запись отсутствующей на ранней стадии сущности как находки превращает реестр в перечень заведомо известного и делает его непригодным для работы.

### 4.5. Шаблон записи находки

Единый и обязательный. Отступления от шаблона не допускаются.

```
### AUD-1.1-014 · S1 · Расхождение со спецификацией · OPEN

Зона:           1.1 Покрытие User Stories
Требование:     US-ORDER-03, критерий приёмки 2
Источник:       specs/06_user_stories/User_Stories_Order_And_Client_Access.md §4.3
Ожидание:       «Повторная отправка формы не создаёт второй заказ»
Наблюдение:     Защита от дубликата отсутствует

                блокирует повторный вызов, идемпотентный ключ в RPC
                create_client_order не передаётся
Влияние:        Двойной клик клиента создаёт два заказа с разными номерами;
                кухня получает два тикета

                на время запроса плюс идемпотентный ключ на стороне RPC
```

## 5. Профили аудита по стадиям

### 5.1. Назначение раздела

План применим на любой стадии проекта, но набор проверяемых зон и цена находок от стадии зависят. Раздел определяет, какие зоны применимы когда, и не позволяет ранней стадии породить реестр из заведомо известных отсутствий.

Стадия объявляется в эпике 0 вместе с базовым коммитом и указывается в шапке каждого отчёта.

### 5.2. Стадии проекта

| Стадия | Признак | Что уже существует |
| --- | --- | --- |
| **Планирование** | Кода нет | Спецификации, функциональная карта, пользовательские истории |
| **Прототип** | Код есть, данные демонстрационные | Интерфейс, заглушки контуров, локальное хранилище |
| **MVP** | Сквозной путь работает на реальных данных | База, роли, основные контуры; часть контуров заглушки |
| **Предрелиз** | Готовится допуск реальных клиентов | Полные контуры, боевая база, публичный адрес |
| **Эксплуатация** | Реальные клиенты и деньги | Всё перечисленное плюс накопленные данные |

Стадия объявляется по фактическому состоянию, а не по намерению. Признаком служит наличие проверяемого, а не планы на него.

### 5.4. Как читать профиль

1. На **стадии планирования** работают четыре зоны: 2, 15, 16 и проверка решений по 12, 14, 17. Именно здесь ревизия дешевле всего: ошибка в модели процесса исправляется правкой документа, а не переписыванием контура.
2. На **прототипе** добавляются зоны кода — 3, 4, 6, 9, 1.4 — и частично 1.1–1.3, 5, 7, 13.
3. На **MVP** применимы девятнадцать зон из двадцати двух.
4. На **предрелизе** применимы все двадцать две, и семь из них становятся обязательными: 11, 13, 14, 18, 19, 21, 22. Это рубеж, на котором отложенные находки предыдущих стадий переходят в высокую критичность.
5. В **эксплуатации** к обязательным добавляется зона 20.

### 5.5. Порядок при неприменимой зоне

Неприменимая зона не пропускается молча. Её эпик выполняется, артефакт создаётся, и в нём фиксируется:

* объявленная стадия проекта;
* обоснование неприменимости со ссылкой на таблицу 5.3;
* стадия, начиная с которой зона становится применимой;
* перечень того, что понадобится проверить, когда эта стадия наступит.

Так следующий аудит получает готовый вход вместо пустого места.

### Эпик 13 — Безопасность

> **Особый порядок.** Эпик спланирован полностью, но выполняется отдельной сессией и отдельной Git-группой. Решение о его запуске принимается отдельно. Другие эпики при встрече с вопросом безопасности ставят пометку `→ зона 13` и анализ не проводят.

**Цель.** Проверить защищённость данных клиентов и разграничение доступа персонала.

**Метод.**

1. Аутентификация: жизненный цикл сессии, обновление и истечение токена, выход, поведение при истёкшей сессии.
2. Разграничение по ролям: возможность доступа роли к чужому разделу через прямой адрес или прямой запрос к базе.
3. Политики доступа на уровне строк: покрытие всех таблиц, полнота по операциям чтения, вставки, изменения и удаления, отсутствие молчаливого отказа.
4. Защита маршрутов: полнота условий в `middleware.ts`, обход через клиентскую навигацию, расхождение между проверкой на клиенте и на сервере.
5. Подтверждение контакта клиента: срок жизни кода, ограничение числа попыток, устойчивость к перебору, различие рабочего и отладочного режимов, отсутствие утечки кода в ответе.
6. Код подтверждения доставки: подпись, срок жизни, повторное использование, подделка, привязка к конкретному заказу.
7. Хранимые функции с повышенными правами: что позволяет вызвать анонимный клиент, полнота проверки входных данных внутри функции.
8. Доступ клиента к заказу: возможность получить чужой заказ подбором идентификатора; то же для переписки по заказу.
9. Валидация входных данных на сервере против валидации только на клиенте.
10. Вывод пользовательского содержимого: переписка, жалобы, комментарии — возможность внедрения разметки.
11. Секреты и окружение: состав публичных переменных, отсутствие служебных ключей на клиенте, история репозитория, вспомогательные скрипты.
12. Утечка данных на клиент: избыточные поля выборок, персональные данные в разметке страницы и в свойствах компонентов.
13. Ограничение частоты действий: создание заказов, отправка кодов подтверждения, сообщения, жалобы.
14. Журнал раскрытия данных: ведётся ли фактически, полон ли, защищён ли от изменения.
15. Уязвимости зависимостей: известные проблемы в установленных версиях.
16. Заголовки безопасности ответа.

**Артефакт.** `../../docs/audit/16_Security.md`

**Критерии готовности.** Все шестнадцать пунктов пройдены; каждая находка снабжена описанием класса проблемы и влияния без пошагового способа воспроизведения атаки.

**Оценка.** `XL`

6. Проверить объявление языка страницы и канонические адреса.

**Артефакт.** `../../docs/audit/21_SEO_And_Metadata.md`

**Критерии готовности.** Каждый пункт проверен с указанием файла; отсутствующие элементы перечислены с оценкой влияния на привлечение клиентов.

**Оценка.** `S`

### Эпик 19 — Устойчивость данных

**Цель.** Оценить защищённость данных от потери.

**Метод.**

1. Проверить наличие в репозитории средств резервного копирования, выгрузки и восстановления.
2. Зафиксировать, что схема базы хранится в миграциях, и оценить, какую часть восстановления это покрывает.
3. Составить опросник по настройкам хранилища: тарифный план, наличие автоматического резервного копирования, глубина хранения копий, проводилась ли проверка восстановления.
4. Оценить, что именно теряется при потере базы: заказы, переписки, меню с изображениями, учётные записи персонала.

**Артефакт.** `../../docs/audit/22_Data_Resilience.md`

**Критерии готовности.** Проверяемое из репозитория проверено; остальное вынесено в опросник со статусом `NOT-VERIFIED` и указанием, где смотреть.

**Оценка.** `S`

### Эпик 20 — Ресурсы и лимиты

**Цель.** Оценить, при каком объёме использования проект упрётся в ограничения платформ.

2. Составить опросник: тарифные планы платформ хранения и размещения, текущее потребление.
3. Описать поведение системы при исчерпании лимита и оценить, будет ли оно заметно персоналу.

**Артефакт.** `../../docs/audit/23_Resources_And_Limits.md`

**Критерии готовности.** Оценка потребления выведена из фактических характеристик кода; вопросы к тарифам вынесены в опросник.

### Эпик 22 — Контент

**Цель.** Проверить наполнение, которое видит клиент.

**Метод.**

2. Выявить дефекты наполнения: пустые описания, отсутствующие изображения, тестовые записи в рабочей базе, архивные позиции, видимые клиенту.

**Артефакт.** `../../docs/audit/25_Content.md`

### Эпик 23 — Консолидация и приоритизация

**Цель.** Свести результаты всех эпиков в единый пригодный к действию документ.

**Вход.** Все отчёты `../../docs/audit/` и наполненный реестр находок.

**Метод.**

1. Свести все находки в `Findings_Register.md`, отсортировать по критичности.
2. Выявить и объединить дубли: одна и та же причина, обнаруженная в разных зонах, должна давать одну находку со ссылками из всех зон.
3. Посчитать метрики: число находок по критичности, по зонам, по типам; доля критериев приёмки в каждом статусе; число `NOT-VERIFIED`; число `N/A` с разбивкой по зонам и указанием стадии, начиная с которой каждая станет применимой.
4. Построить приоритизацию по паре «критичность — стоимость исправления»; выделить быстрые исправления с высокой отдачей.
5. Сгруппировать находки в связанные блоки работ — заготовку структуры будущего плана исправлений.
6. Свести все `NOT-VERIFIED` в один перечень с указанием, что требуется и от кого.
7. Свести все `N/A` в перечень «к следующей стадии»: что именно потребуется проверить, когда проект перейдёт на следующую стадию, и какую критичность находка получит тогда. Этот перечень является прямым входом для повторного применения плана.
7. Зафиксировать расхождение базового и конечного состояния репозитория согласно правилу 3.4.

**Артефакт.** `../../docs/audit/Audit_Summary.md`, финализированный `Findings_Register.md`.

**Критерии готовности.** Каждая находка из отчётов присутствует в реестре; дубли объединены; метрики посчитаны; перечень `NOT-VERIFIED` полон.

**Оценка.** `M`

## 10. Порядок работы с планом

1. Перед началом каждой группы её содержание разъясняется пользователю, спорные моменты выносятся отдельно, работа начинается после согласия.
2. Выполненная группа отмечается в разделе 7 настоящего файла отметкой о выполнении с датой и номером запроса на слияние.
3. Фиксация изменений, отправка в удалённый репозиторий, запрос на слияние и само слияние выполняются только по явной просьбе пользователя. Слияние выполняет пользователь.
4. Каждая группа сопровождается записью в `../../docs/CHANGELOG.md`.
5. План остаётся в `active/` до выполнения всех групп, ручной проверки результата и явного подтверждения пользователя, согласно правилу 8 документа `../README.md`.

### 10.1. Повторное применение плана

План рассчитан на многократное применение: на текущей стадии, перед допуском реальных клиентов и в эксплуатации. Повторный аудит оформляется так:

1. Завершённый план не переписывается и не переиспользуется — согласно правилу 8 документа `../completed/README.md` новая работа оформляется отдельным активным планом.
2. Новый план создаётся копией завершённого с новым порядковым обозначением, новой базовой линией и новой объявленной стадией.
3. Отчёты предыдущего аудита сохраняются: новый набор артефактов размещается в собственном подразделе `../../docs/audit/`, а не поверх прежнего.
4. Перечень `N/A` «к следующей стадии» из эпика 23 предыдущего аудита становится входом нового: эти зоны проверяются первыми.
5. Реестр находок предыдущего аудита сверяется построчно: каждая находка получает вердикт «исправлена», «сохранилась», «изменила критичность в связи со сменой стадии». Это даёт измеримую динамику состояния проекта между ревизиями.
6. Числовые характеристики проекта, зафиксированные в настоящем плане (число пользовательских историй, спецификаций, миграций, панелей, модальных окон), перепроверяются и обновляются в эпике 0 нового аудита. Устаревание этих чисел не мешает повторному применению.

## 11. Открытые вопросы

1. **Момент выпуска сводного отчёта.** Раздел 8.2 предлагает выпускать сводку по двадцати одной зоне, не дожидаясь сессии по безопасности. Требуется подтверждение.
2. **Порядок групп 5–12.** Группы независимы; текущий порядок предложен по убыванию технической значимости. Если приоритет иной, порядок меняется без последствий.
3. **Зоны, требующие участия пользователя** (14, 15, 19, 20, 22). Опросники будут подготовлены аудитом, но ответы даёт пользователь или персонал кафе. Требуется решение, заполняются ли они по ходу или после завершения технических групп.
4. **Судьба находок уровня `S4`.** Косметические находки могут составить значительную долю реестра. Требуется решение, фиксировать их поимённо или сводить в обобщённые записи.

## 12. За пределами плана

Настоящий план охватывает двадцать две зоны. Вне его границ намеренно остаются:

* Нагрузочное и стрессовое тестирование — требует рабочего стенда и сценариев нагрузки.
* Аудит удобства использования с участием реальных клиентов — требует организации наблюдений.
* Финансовая модель и юнит-экономика доставки — не относится к состоянию системы.
* Оценка работы поставщиков платформ размещения и хранения данных.

Эти области могут стать предметом отдельных планов и в настоящем не оцениваются.
