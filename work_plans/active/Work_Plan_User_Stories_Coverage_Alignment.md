## 1. Цель плана

Последовательно привести User Stories в соответствие с текущим проектом DAYMOHKCOFEE, не пытаясь переработать весь слой документации за один проход.

План должен:

1. закрыть найденные расхождения между Functional Map, Feature Specs, Technical Specs, User Stories, активными Work Plans и кодом;
2. добавить отсутствующие пользовательские сценарии, прежде всего для электронной кухни KDS;
3. разделить перегруженные US-02 и US-13 на истории разумного размера;
4. дополнить критические edge cases без превращения каждого сообщения или проверки поля в отдельную историю;
5. обновить трассировку и итоговые check reports только после завершения содержательных эпиков;
6. подготовить надежную документационную основу для отдельного плана исправлений реализации.

Этот Work Plan изменяет только документацию. Изменения кода, базы данных и UI в него не входят.

## 2. Правила размера эпиков и историй

### 2.1 Размер эпика

Один эпик закрывает один связный пользовательский процесс и обычно содержит от 3 до 6 User Stories или сопоставимых сценариев.

Эпик необходимо разделить, если в нем одновременно появляются:

* разные независимые бизнес-результаты;
* более двух основных ролей с разными целями;
* несколько самостоятельных жизненных циклов;
* больше 6 историй;
* необходимость менять несвязанные Feature Specs.

Эпик не нужно дробить, если различия сводятся только к сообщению об ошибке, одному полю формы, одному UI-состоянию или альтернативе того же пользовательского результата.

### 2.2 Размер User Story

Каждая User Story должна иметь:

* одного основного актора;
* одну пользовательскую цель;
* один наблюдаемый результат;
* ориентировочно 4–9 шагов основного сценария;
* не более 6 содержательных альтернатив;
* ориентировочно 4–8 проверяемых критериев приемки.

Если история превышает эти границы из-за второго пользовательского результата или отдельного жизненного цикла, она разделяется. Если превышение вызвано только вариантами одной проверки, варианты остаются внутри одной истории.

### 2.3 Граница между слоями

* бизнес-решение сначала фиксируется в Functional Map или Feature Spec;
* техническое ограничение фиксируется в Technical Spec;
* путь пользователя и проверяемый результат фиксируются в User Stories;
* названия технологий, SQL, API и внутренние механизмы не должны перегружать текст User Story;
* Work Plan не используется для молчаливого создания нового поведения.

## 3. Последовательность выполнения и публикации

Эпики выполняются строго по порядку: `A → B → C → D → E → F → G → H → I → J → K`.

Публикация выполняется восемью Git-группами. Одна Git-группа содержит один или два тесно связанных эпика и выпускается одним push и одним Pull Request.

### 3.1 Git-группы

| Группа | Эпики | Ветка | Единица публикации |
| --- | --- | --- | --- |
| 1. Основа | A | `feat/us-product-scope` | один push и один PR |
| 2. Кухня | B | `feat/us-kitchen-kds` | один push и один PR |
| 3. Персонал | C | `feat/us-staff-access` | один push и один PR |
| 4. Клиентский заказ | D → E | `feat/us-order-and-client-access` | один push и один PR после обоих эпиков |
| 5. Урегулирование | F → G | `feat/us-resolution-and-risk` | один push и один PR после обоих эпиков |
| 6. Выполнение заказа | H → I | `feat/us-delivery-and-discounts` | один push и один PR после обоих эпиков |
| 7. Жалобы | J | `feat/us-complaints` | один push и один PR |
| 8. Финальный аудит | K | `feat/us-final-coverage-audit` | один push и один PR |

### 3.2 Цикл Git-группы

Для каждой Git-группы действует одинаковый цикл:

1. синхронизировать `main` после merge предыдущей Git-группы;
2. создать ветку Git-группы из таблицы выше от актуального `main`;
3. прочитать только документы первого эпика группы;
4. сначала устранить конфликт верхнего слоя;
5. затем актуализировать Technical Specs, если это требуется;
6. только после этого создать или переработать User Stories;
7. выполнить локальную проверку покрытия эпика;
8. обновить CHANGELOG и сделать отдельный локальный commit эпика только после явного запроса пользователя;
9. предоставить пользователю отчет и дождаться подтверждения закрытия эпика;
10. если в группе есть второй эпик, перейти к нему только после закрытия первого, оставаясь в той же ветке;
11. после закрытия всех эпиков группы выполнить общие `npm run typecheck` и `npm run build`;
12. одним push отправить все локальные коммиты группы и подготовить один Pull Request только после явного запроса пользователя;
13. следующую Git-группу не начинать до merge текущей группы и синхронизации `main`.

Одновременная работа над двумя эпиками или двумя Git-группами запрещена. Наличие двух эпиков в одной ветке не разрешает смешивать их изменения: сначала полностью закрывается первый эпик, затем начинается второй.

## 4. Эпик A — границы текущего продукта и поэтапного запуска

Устранить верхнеуровневую неоднозначность между бумажной кухней, KDS, полным целевым потоком и временными fallback-сценариями Block 1/Block 2.

### Шаги

1. Сопоставить Global Spec и Functional Map с текущими Feature Specs кухни, курьера и урегулирования.
2. Зафиксировать KDS как дополнительный операционный путь, не отменяющий бумажную кухню.
3. Отделить целевое поведение продукта от временного релизного ограничения.
4. Проверить WhatsApp-fallback курьера и временную работу без полноценного кабинета урегулирования.
5. Если временный fallback меняет бизнес-процесс, закрепить его в соответствующем Feature Spec; если это только ограничение релиза — оставить его явно ограниченным Work Plan.
6. Обновить статусы и ссылки в индексах, которые всё ещё указывают на уже завершенные readiness-планы как активные.

### Основные документы

* `../../specs/02_functional_map/Functional_Map.md`
* `../../specs/03_feature_specs/Feature_Kitchen_Ticket.md`
* `../../specs/03_feature_specs/Feature_Courier_Delivery.md`
* `../../specs/03_feature_specs/Feature_Resolution_Department.md`
* `Work_Plan_Block_1_Lightweight_Launch.md`
* `Work_Plan_Block_2_Ops_Auth_Polish.md`

### Gate завершения

* бумажная кухня и KDS не противоречат друг другу;
* целевой продукт и временный релизный fallback явно разделены;
* нижние документы не создают неподдержанное верхним слоем поведение;
* следующий эпик может писать KDS User Stories без продуктовых догадок.

### Результат проработки — 2026-09-01

4. Устаревшие ссылки на завершенные readiness/MVP-планы и отсутствующий визуальный слой исправлены в индексах.
5. Все критерии gate выполнены; эпик подтвержден пользователем 2026-09-01 и готов к публикации Git-группы 1.

## 5. Эпик B — электронная кухня KDS

### Цель

Создать отдельный набор историй повара и закрыть полный пользовательский путь электронной кухни.

### Предлагаемый состав историй

1. `US-KDS-01` — повар видит очередь заказов, которые реально переданы на кухню.
2. `US-KDS-02` — повар видит состав и комментарии без клиентских и платежных данных.
3. `US-KDS-03` — повар контролирует норматив и текущий таймер приготовления.
4. `US-KDS-04` — повар отмечает заказ готовым без блокирующего опросника.
5. `US-KDS-05` — менеджер получает результат готовности и может назначить курьера.
6. `US-KDS-06` — кухня продолжает работу через бумажный fallback при недоступности KDS.

### Шаги

1. Актуализировать раздел `User Stories должны проверить` в `Feature_Kitchen_Ticket.md`.
2. Проверить технические правила времени, Realtime, повторного нажатия и восстановления после разрыва соединения.

4. Не дублировать бумажный сценарий US-04; добавить на него ссылку как на fallback.
5. Добавить документ в `../../specs/06_user_stories/README.md`.

### Gate завершения

* роль повара имеет полный, но ограниченный путь;
* повторное действие «ГОТОВО» не создает повторных событий;
* KDS не раскрывает адрес, контакт, пол или оплату клиента;
* бумажный режим остается рабочей альтернативой.

### Результат проработки — 2026-09-01

2. Устранено противоречие в модели данных: `Готовится` и серверные метки времени поддерживают как KDS, так и бумажный fallback.
3. CRM workflow использует одну атомарную операцию готовности для ролей `MANAGER` и `KITCHEN`; повторное действие не создает второе событие.
4. Создан `User_Stories_Kitchen_KDS.md` с шестью историями, а бумажная US-04 сохранена как самостоятельный fallback.
5. Все критерии gate покрыты документацией; эпик подтвержден пользователем 2026-09-01 и готов к commit и публикации Git-группы 2.

## 6. Эпик C — вход персонала, роли и жизненный цикл доступа

### Цель

Согласовать полную модель ролей с поэтапной выдачей учетных записей и закрыть пользовательские сценарии сессии.

### Предлагаемые изменения историй

1. Актуализировать US-ADM-01: добавить роль `KITCHEN` в полную модель ролей.
2. Оставить фазность Block 2: сейчас учетные записи выдаются только `ADMIN` и `MANAGER`.
3. Разделить текущую US-ADM-09 на:
   * вход сотрудника;
   * защита маршрута по роли;
   * прекращение доступа отключенного сотрудника.
4. Сохранить навигацию US-ADM-10 отдельной историей, не смешивая ее с аутентификацией.

### Обязательные edge cases

* неверный логин или пароль;
* отсутствующая или истекшая сессия;
* попытка открыть экран чужой роли;
* отключение сотрудника при уже открытой сессии;
* запрет отключения последнего активного администратора;
* выход из системы.

### Gate завершения

* Feature Spec, Technical Spec и User Stories используют одну модель ролей;
* пользовательские истории не зависят от названия конкретного auth-провайдера;
* фазность учетных записей не воспринимается как удаление будущих ролей;
* безопасность активной сессии проверяется критериями приемки.

### Результат проработки — 2026-09-01

1. Feature Spec и обе Technical Specs приведены к единой модели из пяти ролей: `ADMIN`, `MANAGER`, `COURIER`, `RESOLUTION_OFFICER`, `KITCHEN`.
2. Фазность сохранена: в Block 2 учетные записи выдаются только `ADMIN` и `MANAGER`, остальные роли остаются частью целевой модели.
3. US-ADM-01 дополнена ролью `KITCHEN`, а перегруженная US-ADM-09 разделена на вход, защиту маршрута и прекращение доступа отключенного сотрудника.
4. User Stories не зависят от конкретного auth-провайдера и покрывают неверные данные, отсутствующую или истекшую сессию, чужой маршрут, выход и отключение уже открытой сессии.
5. US-ADM-10 сохранена отдельной навигационной историей; все критерии gate покрыты, эпик подтвержден пользователем 2026-09-01 и готов к commit Git-группы 3.

## 7. Эпик D — оформление заказа и подтверждение контакта

### Цель

Разделить перегруженную US-02 на связный эпик оформления заказа без потери существующих правил.

### Предлагаемый состав историй

1. `US-ORDER-01` — клиент указывает данные доставки и способ оплаты.
2. `US-VERIFY-01` — клиент запрашивает OTP через Telegram или Email.
3. `US-VERIFY-02` — клиент подтверждает канал либо проходит retry/expiry-сценарий.
4. `US-ORDER-02` — клиент проверяет данные и финально отправляет заказ.
5. `US-ORDER-03` — система не создает дубликат при повторной отправке.

Кросс-девайс-доступ не включается в этот эпик и переносится в эпик E.

### Обязательные edge cases

* отказ браузера предоставить геолокацию и разрешенный альтернативный путь;
* отсутствующая геолокация;
* изменение корзины после подтверждения канала;
* три неверных OTP;
* повторная отправка раньше разрешенного срока;
* истекший OTP;
* подтвержденный канал без финальной отправки;
* повторное нажатие финальной отправки.

### Gate завершения

* ни одна история не объединяет одновременно доставку, OTP, финальную отправку и восстановление доступа;
* исходные правила US-02 не потеряны;
* каждая история тестируется отдельно;
* неподтвержденная попытка передается в эпик F только как входное событие.

### Результат проработки — 2026-09-01

1. Перегруженная `US-02` разбита на пять историй в новом `User_Stories_Order_And_Client_Access.md`: `US-ORDER-01`, `US-VERIFY-01`, `US-VERIFY-02`, `US-ORDER-02`, `US-ORDER-03`. Каждая история имеет одного актора, один результат и отдельные критерии приёмки.
2. Feature Specs `Feature_Order_Entry` и `Feature_Contact_Confirmation` уже содержали нужные проверки — бизнес-решения не менялись, эпик остался в границах слоя User Stories.
3. `Technical_Order_Data_Model` (v1.5) получил два уточнения без изменения модели данных: идемпотентность финальной отправки (§3, §15 п.11) и отказ браузера в геолокации как штатный путь со ссылкой Google Maps (§7, §15 п.12).
4. `US-02` в `User_Stories_MVP_Order_Flow.md` (v1.2) ужата до краткой сквозной истории со ссылкой на детальный документ; ключевые правила и сквозные критерии приёмки сохранены.
5. Обработка неподтверждённой попытки не дублируется: `US-VERIFY-02` передаёт её в `US-13` (эпик F) только как входное событие с сохранённым требованием идемпотентности.
6. Кросс-девайс-доступ в эпик D не включён и вынесен в эпик E того же документа.
7. Новый документ зарегистрирован в `specs/06_user_stories/README.md`. Все критерии gate выполнены; эпик подтвержден пользователем 2026-09-01 и подготовлен к commit Git-группы 4. Следующий шаг — эпик E в той же ветке.

## 8. Эпик E — возврат клиента к заказу и чату

### Цель

Описать отдельный жизненный цикл доступа клиента после создания заказа.

### Предлагаемый состав историй

1. `US-ACCESS-01` — клиент сохраняет номер заказа и код доступа.
2. `US-ACCESS-02` — клиент открывает заказ и чат с другого устройства.
3. `US-ACCESS-03` — система безопасно отклоняет неверный или чрезмерно часто вводимый код.
4. `US-ACCESS-04` — клиент видит допустимое состояние заказа и чата после закрытия и архивирования.

### Решения, которые нельзя придумывать на уровне User Stories

До написания соответствующей истории Feature Spec должен решить:

* можно ли восстановить потерянный код;
* можно ли перевыпустить код;
* как клиент получает список нескольких заказов на новом устройстве;
* что показывается после окончания срока доступа.

### Gate завершения

* happy path и ошибки доступа описаны отдельно от оформления заказа;
* номер заказа без кода не дает доступ к данным;
* срок чата и срок доступа не противоречат друг другу;
* открытые продуктовые решения явно закрыты или вынесены за границу текущего релиза.

### Результат проработки — 2026-09-01

1. Снят конфликт верхнего слоя: `Functional_Map.md` v1.7 §6.3 больше не говорит про «повторную OTP-проверку канала на другом устройстве», а описывает возврат по паре «номер заказа + код доступа» — в соответствие с уже обновлёнными Feature Specs.
2. Закрыты четыре продуктовых решения в Feature Specs (`Feature_Client_Chat` v1.2 §6.1/§16, `Feature_Client_Tracking` v1.2 §16):
   * потерянный код перевыпускает менеджер из карточки заказа в CRM (авто-восстановление клиенту не даётся);
   * перевыпуск разрешён, выполняет его менеджер, прежний код после этого недействителен, событие журналируется;
   * на чужом устройстве доступ всегда по одному заказу за раз, общего списка заказов клиента там нет;
   * срок доступа по паре «номер + код» совпадает со сроком чата — активный заказ всегда, после закрытия 30 дней, затем доступ по коду закрывается.
3. Technical Specs синхронизированы: `Technical_Order_Data_Model` v1.6 (`expires_at`, перевыпуск, один заказ на проверку — §13, §15 пп. 13–14), `Technical_Client_Page_Chat` v1.3 (rate limiting ввода пары, перевыпуск, срок — §2, §7), `Technical_Access_Audit` v1.5 (менеджерский перевыпуск и журналирование — §9, §18 пп. 12–14). ## 11. Эпик H — доставка, QR и закрытие оплаты

### Цель

Дополнить существующие истории надежными, видимыми пользователю сценариями доставки и закрытия заказа.

### Точечные доработки

1. Повторное сканирование использованного QR возвращает уже подтвержденный результат и не создает повторного события.
2. QR другого заказа или другого назначения отклоняется.
3. Fallback требует причину и остается видимым менеджеру.
4. Повторное подтверждение наличной оплаты не создает вторую запись.
5. Конкурентные попытки закрыть заказ дают один итоговый переход.
6. Заказ не закрывается, если подтверждена только доставка или только оплата.

### Gate завершения

* User Stories покрывают одноразовость QR на наблюдаемом уровне;
* критерии приемки согласованы с `Technical_Payment_Delivery.md` и `Technical_Order_CRM_Workflow.md`;
* техническая атомарность не переписывается в пользовательскую историю как SQL-реализация.

## 12. Эпик I — ограниченные скидочные товары

### Цель

Закрыть конкурентные и повторные операции продажи ограниченного скидочного товара.

### Точечные доработки

1. Два клиента одновременно пытаются купить последнюю единицу — успешным становится только один заказ.
2. Проданный или списанный товар сразу становится недоступным остальным клиентам.
3. Повторная операция не создает второй связанный заказ.
4. Фиксированная скидка возвращенного заказа не смешивается с общими скидочными товарами, если верхний Feature Spec не разрешает диапазон.

### Gate завершения

* ограниченный товар невозможно продать дважды;
* правило скидки 40% однозначно отделено от настраиваемых скидок;
* повторная операция не создает дублирующую продажу или второй связанный заказ.

## 13. Эпик J — жалобы и доказательства

### Цель

Проверить полный путь жалобы и устранить неподдержанное верхним слоем упоминание вложений в Technical Specs.

### Предлагаемый состав историй

1. `US-COMP-01` — клиент подает жалобу с номером заказа или без него.
2. `US-COMP-02` — клиент получает подтверждение и может приложить разрешенное доказательство, только если эта возможность утверждена в Feature Spec.
3. `US-COMP-03` — администратор просматривает жалобу и доказательства, фиксирует категорию и результат.
4. `US-COMP-04` — жалоба закрывается, архивируется и сохраняет журнал без физического удаления.

### Шаги

1. Проверить упоминание фотографий и вложений в Technical Specs против `Feature_Complaints.md`.
2. Если вложения входят в продукт — определить типы, ограничения и права сначала в Feature Spec, затем в Technical Spec и User Stories.
3. Если вложения не входят в текущий релиз — явно перенести их в post-MVP и не обещать текущей реализацией.
4. Разделить клиентскую подачу и административную обработку, не повторяя целиком US-12 и US-ADM-05/06.

### Gate завершения

* Technical Spec не обещает вложения без поддержки Feature Spec и User Stories;
* клиентский путь и административный lifecycle проверяются отдельными историями;
* права на просмотр, закрытие, архивирование и хранение жалобы однозначны;
* обычный чат не превращается в жалобу автоматически.
