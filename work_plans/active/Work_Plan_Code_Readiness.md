---

## 1. Назначение

Этот план устраняет документационные, продуктовые, архитектурные и инженерные блокеры перед созданием первого кода проекта.

План состоит из семи последовательных групп. Каждая группа выполняется в отдельной ветке, но все семь групп являются этапами одного Work Plan. План остается в `active/` до завершения всех групп и итогового подтверждения пользователя.

---

## 2. Ожидаемый результат

После завершения плана:

1. правила работы с планами, ветками и roadmap не противоречат друг другу;
2. продуктовые спецификации согласованы и имеют честные статусы;
3. архитектура Next.js, Vercel и Supabase зафиксирована без конкурирующих источников истины;
4. модель данных, доступ, авторизация и безопасность Supabase описаны до реализации;
5. критические доменные операции и внешние интеграции имеют надежные технические правила;
6. стратегия тестирования, CI и публикации определена;
7. визуальные правила и итоговые readiness gates закрыты;
8. можно создать ветку `feat/platform-foundation` и начать писать код.

---

## 3. Правила выполнения

1. Одновременно выполняется только одна группа.
2. Каждая группа получает отдельную ветку от актуального и чистого `main`.
3. Следующая ветка создается только после проверки, публикации, merge предыдущей группы и синхронизации локального `main`.
4. Промежуточные commit, push и pull request отдельной группы не завершают весь Work Plan.
5. После каждой группы в этом файле обновляются статус группы, подтвержденный результат и следующий шаг.
6. Решения нижнего уровня не меняют бизнес-смысл документов верхнего уровня.
7. Код приложения не создается ни в одной из семи документационных групп.
8. После завершения всех групп пользователь вручную проверяет итоговый комплект документов, явно подтверждает завершение всего плана и просит подготовить его финальную публикацию.
9. Только после выполнения всех этих условий план переносится в `../completed/`, обновляются индексы и затронутые журналы `../../roadmap/`.

## 5. Группа 1. Governance и workflow

**Цель:** создать непротиворечивый процесс для одного плана, который выполняется через несколько последовательных веток.

Работы:

1. согласовать lifecycle Work Plan во всех README и инструкциях агентов;
2. разрешить промежуточные Git-действия, не завершая активный план;
3. закрепить правило последовательных веток от актуального `main`;
4. исправить некорректные относительные ссылки;
5. устранить цикл источников между Technical Spec и Work Plan;
6. добавить отдельный roadmap для backend и инфраструктуры;
7. проверить индексы и целостность измененной документации.

Критерии готовности:

* во всех правилах используется один и тот же триггер завершения плана;
* промежуточная публикация этапа не перемещает весь план в `completed/`;
* все исправленные относительные ссылки разрешаются;
* Technical Specs являются источником технических решений для Work Plans, а не наоборот;
* `roadmap/Backend_Infrastructure_Roadmap.md` существует и включен в индекс;
* изменения ограничены документацией первой группы.

Результат реализации группы на 2026-07-25:

* создан и проиндексирован единый Work Plan семи групп;
* lifecycle активных и завершенных планов согласован во всех правилах;
* закреплена последовательная работа по одной группе и одной ветке;
* исправлены две относительные ссылки и направление зависимости Technical Spec → Work Plan;
* создан и проиндексирован roadmap для backend и инфраструктуры;
* проверки ссылок, маркеров, структуры групп и `git diff --check` пройдены;
* две независимые read-only проверки завершились без замечаний.

Пользователь проверил группу 1; PR #30 смержен коммитом `bd2469a`, локальный `main` синхронизирован. Группа завершена.

## 6. Группа 2. Согласованность продуктовых спецификаций

**Цель:** убрать продуктовые противоречия, которые нельзя безопасно разрешать на уровне технической реализации.

Работы:

1. проверить согласованность Global Spec, Functional Map, Feature Specs и User Stories;
2. вынести конфликт порога желтого риска на явное решение пользователя и после утверждения закрепить одно правило;
3. вынести конфликт удаления и архивирования сотрудника на явное решение пользователя, сохранив обязательную целостность истории и `AuditLog`;
4. проверить роли, статусы, переходы, сроки хранения и права доступа;
5. изменить статус `Черновик` только у действительно проверенных документов;
6. обновить соответствующие check reports и индексы.

Критерии готовности:

* одна бизнес-ситуация не имеет разных правил в разных документах;
* ни один нижний документ не расширяет Global Spec или Feature Specs;
* источники следующей технической группы имеют честные статусы;
* нерешенные продуктовые вопросы явно остановлены для отдельного решения пользователя.

Первичный аудит группы 2 завершен 2026-07-25. Пользователь подтвердил следующие решения:

1. желтый риск создается при 4 или более совпавших нормализованных категориях без весов; после одного подтвержденного повторения активная желтая запись становится красной; красное ограничение действует до явного снятия отделом урегулирования;
2. lifecycle сотрудника: `Активен` -> `Отключен` -> `Архив`; из `Отключен` доступно восстановление в `Активен`; hard delete и восстановление из `Архив` отсутствуют; карточка сотрудника и append-only `AuditLog` сохраняются;
3. `Owner` является бизнес-персоной, использующей роль `Администратор`; отдельная техническая роль `Owner` в MVP не создается; последнего активного администратора нельзя отключить, архивировать или перевести на другую роль;
4. оплата хранится как отдельное состояние и не является статусом заказа или доставки; `Закрыт` разрешен только при одновременном наличии подтвержденной доставки и оплаты.

Дополнительно проверены и финализированы честные статусы Feature Specs, Technical Specs, User Stories, check reports и основного MVP Work Plan.

Решения синхронизированы сверху вниз, повторные независимые проверки завершены, check reports актуализированы, статусы всех проверенных спецификаций переведены в `Проверено` (версии 1.0). Группа 2 официально завершена.

Следующий шаг: перейти к Группе 3 («Архитектура Vercel и Supabase») в отдельной ветке `docs/vercel-supabase-architecture`.

## 7. Группа 3. Архитектура Vercel и Supabase

**Цель:** зафиксировать целевую архитектуру MVP для публикации на Vercel и backend на Supabase.

Работы:

1. проверить действующее решение Next.js и TypeScript и зафиксировать поддерживаемую Vercel-модель приложения в Technical Spec;
2. зафиксировать Vercel как runtime и платформу публикации;
3. определить и зафиксировать в Technical Spec, какие возможности Supabase требуются MVP помимо PostgreSQL;
4. определить границы ответственности Next.js server-side слоя, database functions и внешних сервисов;
5. принять и зафиксировать в Technical Spec отдельное решение о единственном владельце схемы и data-access, включая роль или исключение Prisma;
6. определить правила использования Realtime, Storage и Edge Functions только для подтвержденных задач;
7. разделить local, preview/staging и production окружения.

Критерии готовности:

* выбор data-access и migrations явно утвержден в Technical Spec и имеет один источник истины;
* каждый backend-процесс имеет одного владельца;
* browser-код не получает привилегированные секреты;
* все новые архитектурные решения сначала зафиксированы в Technical Specs, а Work Plans только используют их;
* старые или неоднозначные утверждения о backend и инфраструктуре устранены.

Результат реализации группы 3 на 2026-07-25:

* зафиксирован технологический стек: Next.js (App Router) на Vercel + Supabase (PostgreSQL, Auth, RLS, Storage, Realtime);
* исключена Prisma из стека MVP во избежание конфликтов владения схемой; единственным владельцем миграций зафиксированы Supabase SQL Migrations (`supabase/migrations/*.sql`);
* дата-аксесс зафиксирован через Supabase JS Client (`@supabase/supabase-js`, `@supabase/ssr`);
* определены границы ответственности между Next.js Server-side (хэширование, rate limiting, внешние API, audit logs), Supabase Database (целостность данных, RLS default-deny, Realtime) и внешними сервисами (Telegram Bot API, SMTP, Vercel Cron);
* разделены конфигурации окружений Local, Preview/Staging и Production;
* спецификация `Technical_MVP_Implementation_Decisions.md` и её индекс в `README.md` актуализированы.

Группа 3 официально завершена.

## 8. Группа 4. Данные, Auth и безопасность Supabase

**Цель:** определить безопасную структуру данных и доступа до создания таблиц и API.

Работы:

1. описать Supabase schemas, таблицы, ограничения, индексы и порядок migrations;
2. определить exposed и private поверхности данных;
3. зафиксировать grants и default-deny RLS policies;
4. определить Supabase Auth и session lifecycle для сотрудников;
5. отделить бизнес-верификацию клиента от учетных записей сотрудников;
6. описать server-only privileged operations и хранение secrets;
7. закрепить минимизацию, маскирование и безопасный поиск персональных данных;
8. определить append-only правила для аудита и истории статусов;
9. подготовить матрицу `роль × объект × состояние × действие`.

Критерии готовности:

* для каждой доступной таблицы или функции определены grants и RLS;
* `anon` не читает заказы, персональные данные и аудит напрямую;
* отключенный сотрудник теряет доступ по определенному сценарию;
* privileged key никогда не используется в клиентском коде;
* для разрешенных операций предусмотрены отрицательные cross-role проверки.

Результат реализации группы 4 на 2026-07-26:

* зафиксировано разделение схем Supabase: публичные таблицы домена в `public`, защищенные служебные таблицы в `private`;
* определен порядок накатки SQL-миграций (`00001_enum_types.sql` -> `00002_core_tables.sql` -> `00003_enable_rls.sql` -> `00004_rls_policies.sql` -> `00005_indexes_and_triggers.sql`);
* активирован принцип `default deny` в RLS для всех таблиц; роли `anon` полностью заблокирован прямой доступ к персональным данным, заказам и `AuditLog`;
* зафиксирован жизненный цикл сотрудников в Supabase Auth с привязкой `auth.jwt() -> 'app_metadata' -> 'role'` и безусловным аннулированием доступа СУБД для статусов `DISABLED` / `ARCHIVED`;
* разграничена бизнес-верификация клиентов (OTP + токен `ClientOrderAccess`) и авторизованный доступ сотрудников;
* зафиксированы правила использования Service Role Key строго на сервере Next.js и хранение секретов в Vercel Environment Variables;
* внедрены append-only SQL-триггеры для защиты журналов от изменений и удалений;
* спецификации `Technical_Access_Audit.md` и `Technical_Order_Data_Model.md` актуализированы.

Группа 4 официально завершена.

## 9. Группа 5. Надежность домена и интеграций

**Цель:** исключить дублирование эффектов, гонки и небезопасные внешние вызовы.

Работы:

1. определить атомарные операции создания заказа и переходов статуса;
2. зафиксировать идемпотентность назначения курьера, доставки, оплаты и закрытия заказа;
3. описать одноразовое потребление QR и защитный fallback;
4. зафиксировать бизнес-OTP для Telegram и Email, rate limits, retries и запрет кодов в логах;
5. определить provider adapters для local и production режимов;
6. описать безопасный процесс ручной платежной ссылки;
7. определить фоновые Cron-задачи, сроки хранения и обработку неуспешных попыток;
8. определить надежность чата и других realtime-сценариев только там, где они нужны MVP.

Критерии готовности:

* повтор запроса не создает второй заказ, платеж или переход;
* конкурентные операции не обходят статусные и риск-ограничения;
* production не может случайно использовать fake OTP;
* внешние интеграции имеют явные timeout, retry, audit и failure rules;
* все решения согласованы с Feature Specs и User Stories.

## 13. Что не входит в этот план

* создание Next.js-приложения;
* установка npm-пакетов;
* создание Supabase-проекта или ресурсов Vercel;
* создание таблиц и migrations;
* реализация UI, API, Auth, RLS или интеграций;
* публикация прикладного кода.

Эти действия начинаются только после полного завершения настоящего Work Plan.
