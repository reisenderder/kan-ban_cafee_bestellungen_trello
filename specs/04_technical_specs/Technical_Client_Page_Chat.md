## 1. Назначение

Документ описывает техническую логику клиентской страницы заказа: получение номера заказа, отображение клиентских этапов, чат по заказу, хранение доступа и автоматические сообщения.

---

## 2. Доступ к странице заказа

После финальной отправки заказа система создает:

* `orderNumber`;
* клиентскую страницу заказа;
* чат по заказу;
* связь между заказом и текущим клиентским устройством/сессией.

Feature Spec не фиксирует технический способ хранения доступа. Technical Spec должен предусмотреть безопасный способ вернуться к чату без полноценной регистрации. Схема `ClientOrderAccess` описана в `Technical_Order_Data_Model.md`.

**(Блок 2)** После подтверждения канала (Telegram/Email OTP) и создания `Order` система
генерирует короткий код доступа (`chat_access_code`, например 4 цифры), связанный с
заказом. Код:

* выдаётся только верифицированному клиенту (нет подтверждения канала — нет кода);
* показывается клиенту при оформлении заказа заметно, с подписью о необходимости
  сохранить его; по возможности дублируется в подтверждении заказа;
* хранится в виде хэша (`Technical_Order_Data_Model.md` §13);
* вместе с номером заказа открывает заказ и чат с любого устройства через RPC-функцию
  (не открытый `SELECT`).

**(Эпик E)** Правила доступа по паре «номер + код»:

* RPC проверки пары проходит через rate limiting до сверки хэша: ограничение на попытки
  по одному номеру заказа, по устройству/сессии и по IP; после превышения — временная
  защитная блокировка, ответ не различает «номер не найден» и «код неверный», чтобы не
  раскрывать существование заказа;
* успешная проверка возвращает данные ровно одного заказа и его чата; список других
  заказов клиента не возвращается, кросс-девайс агрегирование по контакту не выполняется;
* доступ действует, пока заказ активен, и 30 дней после закрытия (совпадает со сроком
  чата); после этого RPC отклоняет пару, история сохраняется;
* менеджер перевыпускает код из карточки заказа в CRM: новый хэш перезаписывает старый,
  новый код показывается менеджеру один раз, событие пишется в журнал заказа, прежний
  код перестаёт действовать. Открытый код клиенту повторно системой не показывается.

---

## 3. Клиентские этапы

Клиент видит только укрупненные этапы:

1. `Заказ принят`;
2. `На кухне`;
3. `Передан курьеру`;
4. `Уже в пути`;
5. `Доставлен`.

Внутренние статусы CRM не раскрываются клиенту.

---

## 4. Чат

Чат привязан к `orderNumber`.

На первом этапе чат поддерживает только текстовые сообщения.

После закрытия заказа чат хранится и остается доступным 30 дней.

В карточке заказа менеджера должен быть счетчик непрочитанных сообщений.

Клиент должен видеть, что менеджер прочитал сообщение.

### 4.1 Схема таблицы chat_messages

| Поле | Тип | Обязательное | Описание |
|------|-----|-------------|----------|
| id | uuid | да | PK, gen_random_uuid() |
| order_id | uuid | да | FK → orders.id |
| sender_type | enum chat_sender_type | да | CLIENT, MANAGER, SYSTEM |
| sender_id | uuid | нет | FK → auth.users.id для MANAGER; null для CLIENT и SYSTEM |
| message_text | text | да | Текст сообщения, макс. 2000 символов |
| is_read | boolean | да | default false |
| created_at | timestamptz | да | Момент отправки |

---

## 5. Автоматические сообщения

Система может писать в чат:

* заказ создан и получил номер;
* заказ перешел на следующий клиентский этап;
* заказ был возвращен в кафе;
* доставка подтверждена;
* заказ закрыт.

Автоматические сообщения не должны раскрывать внутренний красный код, урегулирование или служебные журналы.

---

## 6. Жалобы

Обычный чат не является жалобой.

Если сообщение стало жалобой или конфликтом, менеджер направляет клиента в отдельный канал жалоб или создает жалобу по установленному правилу.

---

## 7. Закрытые решения

1. Доступ клиента к странице заказа хранится через безопасный локальный токен на устройстве и серверную запись связи с заказом. Токен не должен содержать персональные данные в открытом виде.
2. Для повторного открытия на том же устройстве номер заказа вводить не нужно. **(Правка Блока 2 — 2026-08-29)** Если клиент открывает заказ с другого устройства, он вводит пару «номер заказа + код доступа». Код доступа выдаётся клиенту после подтверждения канала (OTP) при оформлении заказа. Эта пара заменяет прежнее требование повторной OTP-проверки подтверждённого канала на новом устройстве. Номер заказа сам по себе достаточным секретом не является; код доступа — является, потому что выдан только верифицированному клиенту.
3. Признак прочтения показывается коротким текстом `Прочитано` рядом с сообщением клиента. Это понятнее, чем только иконка.
4. Частота сообщений ограничивается: не больше 5 сообщений подряд без ответа менеджера и не больше 30 сообщений в час по одному заказу. При превышении лимита клиент видит мягкое ограничение.
5. Через 30 дней чат переводится в архив и становится недоступен для новых сообщений клиента. История сохраняется для внутреннего аудита по правилам хранения, но клиент больше не пишет в этот чат.
6. **(Эпик E)** Ввод пары «номер + код» защищён rate limiting по номеру, устройству/сессии и IP; ответ не раскрывает, существует ли заказ. Одна успешная проверка открывает ровно один заказ.
7. **(Эпик E)** Срок доступа по паре «номер + код» = срок чата: активный заказ — всегда, после закрытия — 30 дней, затем пара больше не открывает страницу заказа.
8. **(Эпик E)** Потерянный код перевыпускает менеджер из карточки заказа в CRM; перезапись хэша, разовый показ нового кода менеджеру, запись в журнал заказа, прежний код недействителен.
