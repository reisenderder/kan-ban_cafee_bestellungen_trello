## 1. Назначение

Документ собирает технические и архитектурные решения для первого MVP-потока заказа. Архитектурный стек зафиксирован под целевую платформу **Vercel** и backend на **Supabase** в рамках Группы 3 плана `../../work_plans/active/Work_Plan_Code_Readiness.md`.

Решения ниже не добавляют новые бизнес-функции. Они выбирают минимальный технический способ реализовать уже утвержденные спецификации: витрину, корзину, оформление заказа, CRM менеджера, кухню, курьера, доставку, оплату, клиентскую страницу, чат, урегулирование, скидочную продажу и жалобы.

---

## 2. Принцип первого MVP

Первый MVP строится как продуктовый контур на базе **Vercel** (приложение Next.js App Router) и **Supabase** (PostgreSQL, Auth, RLS, Realtime, Storage).

Приоритеты:

1. быстрый переход к рабочему прототипу;
2. единая модель данных PostgreSQL под управлением Supabase SQL Migrations;
3. строгие роли и контекстный доступ через Supabase RLS (Row Level Security) и Next.js Middleware;
4. разграничение публичной и привилегированной поверхности;
5. возможность развивать систему без конкурирующих ORM и разделения источников схемы.

---

## 3. Решение по архитектурному стеку Vercel и Supabase

Для MVP зафиксирован следующий технологический стек:

1. **Платформа публикации и runtime**: **Vercel** (Serverless/Node.js Runtime).
2. **Frontend и Server-side слой**: **Next.js (App Router)** с **TypeScript**.
3. **UI и Styling**: React-компоненты внутри Next.js с Vanilla CSS / CSS Modules.
4. **Backend и База данных**: **Supabase (PostgreSQL)**.
5. **Единственный владелец схемы данных и миграций**: **Supabase SQL Migrations (`supabase/migrations/*.sql`)**. ORM Prisma исключена из стека MVP для предотвращения конфликтов владения схемой, RLS-политиками и типами.
6. **Data-access слой**: **Supabase JS Client (`@supabase/supabase-js`, `@supabase/ssr`)**.
7. **Аутентификация сотрудников**: **Supabase Auth** (email/password для персонала с привязкой к таблице профилей и ролей).
8. **Фоновые задачи и Cron**: Vercel Cron Jobs для периодических операций (очистка устаревших токенов, архивация чатов).
9. **Валидация данных**: TypeScript-схемы (Zod) на границе форм, Server Actions и API Route Handlers.

Причина выбора сочетания Next.js (Vercel) + Supabase:

* Vercel обеспечивает мгновенную публикацию, preview-окружения для PR и масштабируемый serverless-runtime для Next.js;
* Supabase предоставляет готовую PostgreSQL базы данных с вшитыми механизмами RLS (Row Level Security), Auth и Realtime;
* Исключение Prisma гарантирует единственный источник истины схемы в виде SQL-миграций Supabase и прямое использование RLS без конфликтов типов.

## 4. Решение по хранению данных и сервисам Supabase

Для MVP используется PostgreSQL в составе платформы Supabase.

Используемые сервисы Supabase:

1. **Supabase Database (PostgreSQL)**: Хранение всех таблиц домена (`orders`, `order_items`, `menu_items`, `verification_requests`, `trusted_channels`, `audit_logs`, `complaints`, `resolution_records` и др.).
2. **Supabase Auth**: Управление учетными записями персонала (администраторы, менеджеры, курьеры, отдел урегулирования) с безопасным хранением сессий и привязкой `auth.uid()` к `AuditLog` и профилям пользователей.
3. **Supabase Row Level Security (RLS)**: Вшитые политики разграничения доступа на уровне строк PostgreSQL. Матрица прав `роль × объект × действие` контролируется на уровне СУБД. По умолчанию действует политика `default deny` (все таблицы закрыты для публичного прямого доступа).
4. **Supabase Storage**: Хранение вложений (фотографий бракованных блюд / прикрепленных материалов по жалобам и возвратам) в защищенных bucket-ах с доступом по подписанным URL.
5. **Supabase Realtime**: Трансляция изменений статусов заказов и сообщений чата в CRM менеджера и клиентскую страницу через WebSocket без применения внешних тяжелых очередей.

Минимальные правила хранения:

1. все рабочие сущности заказа хранятся в PostgreSQL Supabase;
2. `OrderStatusHistory` и `OrderEventLog` (`AuditLog`) являются append-only;
3. чувствительные данные хранятся отдельно от обычных рабочих данных;
4. для поиска доверенных каналов используются нормализованные значения и хэши;
5. открытые Telegram, Email и телефон не используются как публичные идентификаторы;
6. удаление важных рабочих записей заменяется архивированием;
7. Service Role Key (привилегированный ключ Supabase) используется **строго только во внутреннем Server-side слое Next.js** и никогда не передается в клиентский браузерный код.

---

## 4.1 Границы ответственности слоев (Next.js vs Supabase vs Внешние сервисы)

1. **Next.js Server-side (Server Actions / Route Handlers)**:
   * Генерация и проверка хэшей OTP, QR-токенов и устройств клиентов;
   * Вызов внешних API (Telegram Bot API, SMTP Email);
   * Проверка rate limits до вызова СУБД или внешних сервисов;
   * Запись привилегированных событий `AuditLog` с использованием изолированного Service Role клиента.

2. **Supabase Database & RLS**:
   * Гарантия целостности данных, внешних ключей и уникальных ограничений;
   * Изоляция доступа по ролям пользователей для обычных операций через Supabase JS Client;
   * Автоматическая генерация Realtime-событий для CRM и клиентской страницы.

3. **Внешние сервисы**:
   * **Telegram Bot API**: отправка OTP клиенту;
   * **SMTP / Email Provider**: отправка OTP клиенту;
   * **Vercel Cron**: фоновые регламентные задачи (очистка устаревших токенов, регламентная архивация).

---

## 4.2 Окружения (Local, Preview, Production)

1. **Local**: Next.js dev server (`npm run dev`) + локальный Supabase через Supabase CLI (`supabase start`). Все секреты берутся из `.env.local`.
2. **Preview / Staging**: Автоматический deployment Vercel Preview при создании PR + изолированный Staging-проект Supabase. Использование производственных данных и секретов запрещено.
3. **Production**: Vercel Production + отдельный Production-проект Supabase. Доступ к Service Role Key строго изолирован в Vercel Environment Variables.

## 5. Решение по OTP

OTP реализуется через два канала:

1. Telegram Bot API для Telegram;
2. SMTP или транзакционный Email-провайдер для Email.

Минимальная логика:

1. сервер создает `VerificationRequest`;
2. сервер генерирует одноразовый код;
3. в базе хранится только хэш OTP;
4. код действует 10 минут;
5. повторная отправка доступна через 60 секунд;
6. после 3 неправильных попыток включается блокировка на 15 минут;
7. после успешной проверки создается или обновляется `TrustedChannel`;
8. доверенный канал действует 1 год.

API-обработчик отправки OTP должен использовать rate limiting middleware до генерации кода и до внешней отправки. Минимальные ограничения: по IP, по устройству/сессии и по выбранному Telegram/Email-каналу. Если лимит превышен, OTP не создается, Telegram Bot API или Email-провайдер не вызывается, а событие фиксируется как защитное ограничение.

Для локальной разработки разрешен dev-режим: OTP не отправляется наружу, а показывается только в серверном логе разработки. В production такой режим должен быть отключен.

## 6. Решение по QR доставки

QR подтверждает доставку, но не оплату.

Технический способ:

1. при назначении курьера система создает одноразовый `DeliveryConfirmationToken`;
2. открытое значение токена показывается только внутри QR;
3. в базе хранится хэш токена, `orderId`, `courierId`, `deliveryAssignmentId`, срок жизни и статус;
4. QR ведет на серверный route подтверждения доставки;
5. после успешного сканирования токен становится недействительным;
6. после закрытия заказа токен также становится недействительным;
7. fallback требует обязательную причину и отдельное событие журнала.

QR нельзя использовать повторно и нельзя использовать для другого заказа или другого назначения курьера.

---

## 7. Решение по клиентской странице заказа

Клиентская страница заказа доступна без полноценной регистрации.

Технический способ:

1. после создания `Order` система создает `ClientOrderAccess`;
2. клиент получает локальный безопасный токен устройства;
3. токен хранится на стороне клиента как локальный доступ к конкретному заказу;
4. на сервере хранится только хэш токена и связь с заказом;
5. токен не содержит персональные данные;
6. доступ действует для активного заказа и 30 дней после закрытия;
7. при открытии с другого устройства клиент вводит номер заказа и проходит дополнительную проверку подтвержденного канала.

Номер заказа сам по себе не является достаточным секретом для доступа к чату и деталям заказа.

## 8. Решение по ролям и правам

Для сотрудников MVP используется ролевая модель из `Technical_Access_Audit.md`:

1. `Администратор`;
2. `Менеджер`;
3. `Курьер`;
4. `Отдел урегулирования`.

`Клиент` и `Система` являются типами actor/principal, но не ролями сотрудников.

`Owner` — бизнес-персона владельца кафе, использующая роль `Администратор`. Отдельная техническая роль `Owner` в MVP не создается.

Проверка доступа строится не только по роли, но и по контексту:

1. роль пользователя;
2. связанный объект: заказ, доставка, жалоба или ситуация;
3. текущее состояние объекта;
4. назначение сотрудника на конкретную задачу;
5. необходимость раскрытия чувствительных данных.

На первом этапе не создается роль `Старший менеджер`. Если позже она понадобится, ее нужно добавить отдельной спецификацией.

Lifecycle сотрудника: `Активен` -> `Отключен` -> `Архив`. Hard delete отсутствует. Последнего активного администратора нельзя отключить, архивировать или перевести на другую роль.

## 9. Решение по журналированию

Для MVP используется единый append-only журнал важных действий.

Минимальная сущность: `AuditLog`.

Минимальные поля:

* `id`;
* `actorId`;
* `actorRole`;
* `action`;
* `objectType`;
* `objectId`;
* `context`;
* `result`;
* `oldValue`;
* `newValue`;
* `createdAt`;
* `source`.

Журналируются:

1. вход сотрудника;
2. изменение ролей и доступов;
3. раскрытие чувствительных данных;
4. создание и подтверждение заказа;
5. передача на кухню;
6. повторная печать кухонного чека;
7. назначение курьера;
8. QR или fallback подтверждение доставки;
9. подтверждение оплаты;
10. отправка платежной ссылки;
11. передача в урегулирование;
12. действия с желтым и красным списком;
13. действия с жалобами;
14. выдача права на скидочный товар.

Обычное открытие карточки без раскрытия чувствительных данных не журналируется как отдельное событие.

`AuditLog` сохраняется при отключении и архивировании сотрудника. Записи журнала не удаляются каскадно вместе с карточкой сотрудника и не переписываются задним числом.

## 10. Решение по ручной платежной ссылке

Автоматическая платежная интеграция не входит в первый MVP.

Технический способ:

1. менеджер создает платежную ссылку во внешнем платежном инструменте;
2. менеджер вручную отправляет ссылку клиенту через утвержденный рабочий процесс;
3. система фиксирует факт отправки ссылки;
4. открытая ссылка не хранится дольше операционной необходимости;
5. в истории хранится безопасный идентификатор или маска ссылки;
6. срок жизни ссылки для первого MVP - 30 минут;
7. оплату подтверждает менеджер вручную;
8. при подтверждении менеджер вводит короткий идентификатор платежа или служебную заметку.

Курьер не подтверждает электронную оплату. Курьер только видит, нужно ли брать наличные.

Состояние оплаты хранится отдельно от статуса заказа и доставки. Подтверждение оплаты само по себе не переводит заказ в `Доставлен`. Переход в `Закрыт` разрешен только при одновременном наличии подтвержденной доставки и подтвержденной оплаты.

## 12. Что не входит в первый технический шаг

В первый технический шаг не входит:

1. полноценная автоматическая платежная интеграция;
2. отдельный backend-сервис вне Next.js;
3. микросервисная архитектура;
4. мобильное приложение;
5. push-уведомления;
6. сложная аналитика;
7. экспорт клиентской базы;
8. финальный UI-kit;
9. автоматический выбор маршрута курьера;
10. автоматическое управление складом.

## 13. Связь с блокерами Work Plan

Work Plan использует решения этого Technical Spec для закрытия своих блокеров:

| Блокер | Решение |
| --- | --- |
| Технологический стек | Next.js (App Router) на Vercel + Supabase (PostgreSQL, Auth, RLS) |
| Хранение данных и миграции | Supabase PostgreSQL + Supabase SQL Migrations + Supabase JS Client (Prisma исключена) |
| OTP | Telegram Bot API + Email, OTP хранится как хэш |
| QR | Одноразовый серверный токен доставки, в базе хранится хэш |
| Доступ клиента к странице заказа | Локальный токен устройства + серверная связь с заказом |
| Роли и права | Supabase Auth + RLS + Контекст + Состояние объекта |
| Журналирование | Единый append-only `AuditLog` |
| Ручная платежная ссылка | Внешняя ссылка, ручная отправка и ручное подтверждение менеджером |

## 14. Критерии готовности

Документ готов к использованию перед кодом, если:

* решения не противоречат существующим Feature Specs, Technical Specs и User Stories;
* каждый блокер Work Plan имеет конкретное техническое решение;
* выбранный стек позволяет реализовать публичные и внутренние страницы в одном MVP;
* модель данных остается совместимой с `Technical_Order_Data_Model.md`;
* OTP, QR, платежная ссылка и клиентский доступ не раскрывают персональные данные в открытом виде;
* роли и журналирование соответствуют `Technical_Access_Audit.md`.

До завершения группы 3 критерии этого раздела не считаются выполненными, а документ не снимает общий блокер на начало кода.
